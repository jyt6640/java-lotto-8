## 📋 **기본 기능 목록**

---

- [X] 로또 번호의 숫자 범위는 1~45까지이다.
- [X] 1개의 로또를 발행할 때 중복되지 않는 6개의 숫자를 뽑는다.
- [X] 당첨 번호 추첨 시 중복되지 않는 숫자 6개와 보너스 번호 1개를 뽑는다.
- [X] 당첨은 1등부터 5등까지 있다. 당첨 기준과 금액은 아래와 같다.
    - [X] 1등: 6개 번호 일치 / 2,000,000,000원
    - [X] 2등: 5개 번호 + 보너스 번호 일치 / 30,000,000원
    - [X] 3등: 5개 번호 일치 / 1,500,000원
    - [X] 4등: 4개 번호 일치 / 50,000원
    - [X] 5등: 3개 번호 일치 / 5,000원
- [X] 로또 구입 금액을 입력하면 구입 금액에 해당하는 만큼 로또를 발행해야 한다.
- [X] 로또 1장의 가격은 1,000원이다.
- [X] 당첨 번호와 보너스 번호를 입력받는다.
- [X] 사용자가 구매한 로또 번호와 당첨 번호를 비교하여 당첨 내역 및 수익률을 출력하고 로또 게임을 종료한다.
- [X] 사용자가 잘못된 값을 입력할 경우 `IllegalArgumentException`을 발생시키고, "[ERROR]"로 시작하는 에러 메시지를 출력 후 그 부분부터 입력을 다시 받는다.
    - `Exception`이 아닌 `IllegalArgumentException`, `IllegalStateException` 등과 같은 명확한 유형을 처리한다.

### 🧾 **입출력 요구 사항**

**입력**

- 로또 구입 금액을 입력 받는다. 구입 금액은 1,000원 단위로 입력 받으며 1,000원으로 나누어 떨어지지 않는 경우 예외 처리한다.

```
14000
```

- 당첨 번호를 입력 받는다. 번호는 쉼표(,)를 기준으로 구분한다.

```
 1,2,3,4,5,6
```

- 보너스 번호를 입력 받는다.

```
7
```

**출력**

- 발행한 로또 수량 및 번호를 출력한다. 로또 번호는 오름차순으로 정렬하여 보여준다.

```
8개를 구매했습니다.
[8, 21, 23, 41, 42, 43] 
[3, 5, 11, 16, 32, 38] 
[7, 11, 16, 35, 36, 44] 
[1, 8, 11, 31, 41, 42] 
[13, 14, 16, 38, 42, 45] 
[7, 11, 30, 40, 42, 43] 
[2, 13, 22, 32, 38, 45] 
[1, 3, 5, 14, 22, 45]
```

- 당첨 내역을 출력한다.

```
3개 일치 (5,000원) - 1개
4개 일치 (50,000원) - 0개
5개 일치 (1,500,000원) - 0개
5개 일치, 보너스 볼 일치 (30,000,000원) - 0개
6개 일치 (2,000,000,000원) - 0개
```

- 수익률은 소수점 둘째 자리에서 반올림한다. (ex. 100.0%, 51.5%, 1,000,000.0%)

```
총 수익률은 62.5%입니다.
```

- 예외 상황 시 에러 문구를 출력해야 한다. 단, 에러 문구는 "[ERROR]"로 시작해야 한다.

```
[ERROR] 로또 번호는 1부터 45 사이의 숫자여야 합니다.
```

- **실행 결과 예시**


## 🤔 이전 문제에 대한 코드 리뷰에서 생각해볼 점

---

### 1. 상수/메시지 관리 관련 리뷰
> 상수를 한 클래스에서 모두 관리한 점은 좋다.<br>
> 다만, 게임과 관련된 상수, 자동차와 관련된 상수는 각 도메인 별로 분리하는 것이 유지보수에 유리하다.<br>

### 2. 클래스/메서드 생성 방식(의존성 관리)에 대한 리뷰
> Controller에서 Service/Validator 등을 직접 new로 생성하지 않고, 외부에서 주입(생성자/메서드 인자)받도록 만드는 것이 더 좋다.<br>
>“클래스 간 결합도를 낮추고, 추후 테스트(특히 Mock 객체 활용) 및 코드 확장에 더 유연해진다”<br>
>그리고 InputView/OutputView 등 외부 리소스 관리 객체도 주입하는 방식으로 바꾸는게 리팩토링 방향에 맞다.

### 3. 상수의 범용화에 대한 추가 리뷰
> 여러 곳에서 쓰지 않는 상수라면 꼭 public static final 등으로 빼기보다는 객체 내에서만 쓰도록 감추는 게 더 안전하고 OOP적인 구조다!

### 4. 기타(코드 컨벤션 등) 리뷰
> 들여쓰기/불필요한 공백, getter/setter 지양 등 기본 컨벤션에 대한 긍정적 피드백 및 추가 조언

### 1. 의존성 주입과 테스트 용이성

> 랜덤 값 테스트의 어려움을 2주차에서 경험했기 때문에, 이번에는 다르게 접근했습니다.<br>
>**문제 인식:**<br>
> - `Randoms.pickUniqueNumbersInRange()`를 직접 호출하면 테스트에서 결과를 예측할 수 없음<br>
> - 매번 랜덤한 번호가 생성되어 테스트 작성이 어려움<br>

> **해결 방법:**<br>
> 인터페이스를 만들어서 실제 구현과 테스트 구현을 분리했습니다.<br>
> - 실제 환경에서는 `LottoNumberGenerator`가 진짜 랜덤 번호를 생성<br>
> - 테스트 환경에서는 `FixedNumberGenerator`가 고정된 번호를 반환<br>
> - `AppConfig`에서 어떤 구현체를 사용할지 결정<br>

> **배운 점:**<br>
> 이전 주차에서는 `@ValueSource`로 여러 값을 넣어가며 테스트했다면, 이번에는 **전략 패턴**과 **의존성 주입**을 통해 아예 동작 방식 자체를 바꾸며 진행했습니다 !<br>
> 덕분에 테스트에서 원하는 로또 번호를 자유롭게 설정할 수 있었고, 예측 가능한 테스트를 작성할 수 있었습니다.<br>
> 
> 모두 일단은 혼자 깨달아가면서 진행 중이기에 옳지 않을 수도 있습니다.<br>
> 리뷰어분들이 있기에 더 배워 갈 수 있고 성장 할 수 있다고 생각합니다.<br>
> 많은 도움 부탁드리겠습니다 !

### 2. 계층 분리와 단일 책임 원칙

> **계층 분리 문제 인식:**
> 우테코 클린코드 체크리스트의 "메서드가 한 가지 일만 담당하도록 구현했는가?"와"3개 이상의 인스턴스 변수를 가진 클래스를 구현하지 않았는가?"를 동시에 고민했습니다.<br>
> 초기에 LottoController가 InputHandler, OutputHandler, LottoPurchaseService, LottoResultService를 모두 직접 의존하고 있어서 인스턴스 변수가 4개였습니다.

>**해결 방법:**
> 먼저 Service들을 LottoGameService라는 Facade로 통합했습니다.<br>
> 복잡한 여러 서비스 호출을 하나의 간단한 인터페이스로 제공하는 방식입니다.
> 그 결과 Controller의 인스턴스 변수를 3개로 줄일 수 있었습니다.
> 
> - InputHandler: 입력 담당
> - OutputHandler: 출력 담당
> - LottoGameService: 게임 로직 담당

> **검증 로직 위치 문제 인식:**
> 당첨 번호를 String에서 List<Integer>로 변환할 때 발생하는 예외를 어디서 처리해야 할까 고민했습니다.

> **해결 방법:**
> 결국 계층별로 책임을 나눴습니다:
> - **InputHandler**: 형식 검증 (공백인지, 쉼표 형식이 맞는지)
> - **InputParser**: 변환 검증 (String을 int로 변환, int 범위 초과 확인)
> - **Domain 객체**: 비즈니스 규칙 검증 (6개인지, 중복인지, 1~45 범위인지)
> 
> 계층별로 책임을 명확히 나누니 각 클래스의 역할이 분명해졌다고 생각듭니다.<br>
> 이 부분도 함께 확인 부탁드립니다!

### 3. 새로운 아키텍처 패턴 적용

> **DTO, Mapper 도입:**<br>
> - View가 Domain을 직접 참조하지 않도록 중간에 DTO와 Mapper를 두었습니다.<br>
> - OutputMapper가 Domain 객체를 DTO로 변환해주는 역할을 하면서, 계층 간 의존성을 낮출 수 있었습니다.<br>

> **패턴 적용:**
> - **Facade 패턴**: LottoGameService로 복잡한 서비스 로직 통합
> - **전략 패턴**: NumberGenerator 인터페이스로 생성 전략 교체
> - **DTO 패턴**: 계층 간 데이터 전달 전용 객체 사용
> - **Mapper 패턴**: Domain과 DTO 변환 로직 분리
>
> 단순히 그냥 서칭을 해보며 최대한 단일 책임 원칙과 getter 사용을 지양하기 위해 노력을 많이 했습니다.<br>
> 이부분도 같이 확인 해주시면 좋을 것 같습니다 !

### 4. 개발 순서에 대한 고민

> 예상했던 구현 순서와 실제 개발 과정이 많이 달랐습니다.<br>
> **계획과 실제:**
> - 계획: 도메인 → 입출력 → 로직 → 예외 처리 (7단계)
> - 실제: 도메인+검증 → 서비스 → 입출력 → 리팩토링 3회 (15단계)
> 
> 처음에는 "일단 돌아가는 코드를 만들자"는 생각으로 최소 기능을 완성했습니다.<br>
> 그 후 테스트를 추가하고, 리팩토링을 여러 번 진행하면서 점진적으로 개선했습니다.

> **도메인 우선 설계:**<br>
> 2주차 자동차 경주에서 도메인을 먼저 설계하고 개발을 시작했을 때 큰 차이를 느꼈기 때문에, 이번에도 도메인부터 탄탄하게 만들려고 노력했습니다.<br>
> - 1주차 문자열 계산기: 배열로 시작 → 컬렉션으로 전환하는 큰 리팩토링 필요
> - 2주차 자동차 경주: 도메인 우선 설계 → 점진적 확장
> - 3주차 로또: 도메인+테스트 동시 → 계층 추가 → 아키텍처 개선

> **아직 남아있는 고민:**
> - 최소한의 개념으로 일단 완성 시킨 후 → 리팩토링
> - 테스트 작성 → 기능 개발 → 즉시 리팩토링
>
> 어떤 방식이 더 효과적일지 계속 고민 중입니다.<br>
> 이번에는 두 번째 방식에 가까웠는데, 덕분에 초기 리팩토링 비용은 줄었지만 대신 후반부에 아키텍처 전체를 개선하는 큰 리팩토링이 필요했습니다.<br>
> 다음 미션에서는 초기 계획 단계에서 아키텍처 설계도 포함해서 진행해보려고 합니다!
